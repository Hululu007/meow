## 实现期实测补充（v0.9.17）

三条只有真跑起来才知道的约束，已写进代码注释与测试：

1. **推理模型要单独给 token 预算**。`deepseek-r1:14b` 在 `max_tokens=300`
   与 `900` 时**全部预算烧在思维链上**，`finish_reason=length` 而 `content`
   是空字符串——用户看到的是「AI 没反应」。抬到 3000 才有正文。
   现按模型名识别（`r1|qwq|reasoner|thinking|o1|o3`）自动兜底到 3000。
2. **系统提示词必须写"反例"**。只写"不要列点"时，小模型仍会输出 Markdown
   列表并推荐 HandBrake / CloudConvert 这类外部工具；补上三条反例后实测
   3/3 用例合格（说人话、不提外部工具、不列点）。
3. **中文 prompt 不要用 shell 内联传参**。Git Bash 会按 GBK 编码发出，
   模型收到乱码后回一句「看起来你分享了乱码」。测试脚本一律从文件读。

实测记录（Ollama `deepseek-r1:14b`，三个典型 case）：

| case | 模型输出 | 判定 |
|---|---|---|
| 占位内容 | 「源站返回了 HTTP 200，但内容不是 m3u8，而是占位页或图片…建议更换其他播放源」 | PASS |
| 编码不支持 | 「浏览器不支持该视频的编码格式（通常是 MKV 或 HEVC）。下一步请等待客户端自动转码」 | PASS |
| 仅弹幕缺失 | 「视频本身没问题，只是这部片没取到弹幕。可以换个弹幕源再试试」 | PASS |

## 实现期实测补充（v0.9.21，端到端对话实测）

用真实后端（56 源）+ 真实模型（`deepseek-v4.1-flash` 走 OECT 网关）跑完整对话，
揪出 **8 个只有真跑起来才暴露的问题**。全部已修，每条都有对应测试。

### A. 工具层（3 个）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| **A1** | `meow_play` 四条线路全部报「详情为空（源可能已失效）」 | `detail`/`play` 用了 **GET + query**，而 `/api/{site}/{action}` 的分派只读 body。**GET 不报错，返回 200 和一个空壳 list**（`vod_name=null`、`vod_play_url` 长度 0），所以极难归因——手动点播放完全正常 | 全部改成 POST + body。实测同参数：GET → 空壳 / POST → `vod_name='庆余年 第一季'` + 6871 字节播放表 |
| **A2** | `meow_live` 永远报「0 个频道」 | 读 `r.channels`，但 `/api/live` 返回的是 `{tried, playlists, groups, failed}`，**没有 channels**。于是"上游全挂（27/27）"和"没配置源"在输出里长得一样 | 按 `groups[].channels` 统计，并把 `failed/tried` 写进摘要 |
| **A3** | `meow_state` / `meow_sources` 报「0 个降级」，实际 17 个 | 只信顶层 `degraded` 数组。健康表是**按需建立**的（某源被调用过才有记录），冷启动时顶层数组为空，但 `sites` 明细里已有 | 以 `sites` 明细为真源，顶层数组只作补充 |

### B. 编排层（3 个）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| **B1** | 死循环熔断失效，`meow_play` 连试 4 次 | 只按「同工具 + **同参数**」判。模型每次重试参数略有不同（有时带 `line` 有时不带），签名全不同 | 增加第二维度：**同工具连续失败 2 次**即终止 |
| **B2** | `max_rounds` 被误报成「分析超时」 | 只判 `stopReason === 'timeout'`，`max_rounds` 落进同一句文案，把"试了 8 轮没搞定"误导成"网络慢" | 三种 stopReason 分开说，并带上具体失败原因 |
| **B3** | 「有哪些台能看直播」直接报超时，实际模型还在思考 | 模型单轮超时 **8 秒**。这是按纯对话估的，没算 function-calling 的开销——9 个工具 schema 要读，推理模型首轮很容易超 | 模型 25s / 工具 30s / 总 90s，三者分开。**★ 这一版没改完**：`callModel` 里的 abort 仍是 8s，见 G1 |

### C. 意图路由（2 个，最影响体验）

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| **C1** | 第二轮「那就放它吧」被拿去当关键词搜索，搜出「扶你青云反成仇，那就放你尘埃」并当结果展示 | **卡片回填用 `meowSearch(text)`**，`text` 是用户原话。多轮里的第二句常不含片名 | 改用 `r.calls` 里 **模型实际传的 `args.keyword`** 回填 |
| **C2** | 各种语义硬编码成正则，越做越歪 | 把模型该做的判断抢过来做。**ZCode 不是这么干的**——它让模型看技能描述来选 | 见 §一之补充「意图路由的三层分工」 |

### D. 工具可见性（1 个，最隐蔽）

`tools.ts` 的 `TOOL_DEFS` 有 9 个，但 `orchestrate.ts` 的 `TOOLS` 只注册了 6 个——
**`meow_danmaku` / `meow_live` / `meow_cache` 模型根本看不见**。用户问"这部为什么没弹幕"时
它只能瞎猜。已补齐，并加测试：从 `tools.ts` 提取所有工具名，逐个断言在 `orchestrate.ts` 注册过。

### E. 对话能力补齐（本轮新增）

之前是「一问一答」：面板只显示最后一条答案，用户看不到自己发过什么，也没有上下文。

- **消息列表**：用户消息右对齐、AI 左对齐，各自留痕；新消息自动滚到底
- **上下文**：设置页 AI 分区可配 `llmHistoryRounds`（默认 5，0–10）。只带「用户问 + 最终回答」，
  **不带工具往返**——工具消息里有几十 KB 搜索结果，会让每轮 prompt 暴涨
- **等待秒数**：模型超时放宽到 25 秒后，「正在分析…」可能静止十几秒，加 `（12s）` 提示

实测对照：修复前「那就放它吧」丢失上文、把整句当关键词搜；修复后 **5 秒**完成
（只调 `meow_play`，零搜索，正确取到地址）。

### F. 裁剪边界的坑

带上历史后，消息裁剪的边界**不能写死 `slice(0, 2)`**——第 0 条是 system、
第 1..N 条是历史问答，写死 2 会把历史当成工具往返裁掉，等于上下文白传。
必须按 `baseLen = 1 + history.length + 1` 算。

### G. 「AI 总是超时」的两个真因（2026-11-02 实机）

用户报「为什么总是超时」，面板上反复出现「分析超时了」。实机取证后是两个
**互相独立**的原因，任一都足以让一轮失败：

| # | 症状 | 真因 | 修法 |
|---|---|---|---|
| **G1** | 每一轮都像被同一条线掐断 | **两层超时叠着、内层更小**：编排层写 25 秒，但 `callModel` 的 `AbortSignal` 用的是偏好 `llmTimeoutMs`（默认 **8000**，设置页根本没有这个字段）。于是 25 秒从未生效，模型只要思考超过 8 秒就必然失败 | `callModel` 接受 `timeoutMs` 覆盖，编排层显式传 `MODEL_ABORT_MS`（= 25s + 3s，让外层竞速先报错、错误文案能指明哪一层） |
| **G2** | 错误原文是「模型返回空内容」，不是超时 | 偏好 `llmMaxTokens` 默认 **300**（按"解释一句话"定的，同样没有 UI）。编排一轮要装下"读 11 个工具 schema + 工具结果 + 想清楚 + 吐 tool_calls 或一段回答"，推理模型把 300 全烧在思维链上 → `finish_reason=length`、content 与 tool_calls 都为空 | ① 编排层给硬下限 `MIN_ROUND_TOKENS=1200`；② `callModel` 见 `finish_reason=length` 且两样都空 → 预算翻 4 倍重试一次（上限 8000）；③ 新装默认 `llmMaxTokens` 300→800 |

两条都**不能靠模型名判断**：`deepseek-v4.1-flash` 名字里没有 r1/reasoner，
`REASONING_MODEL_RE` 永远匹配不到，但 `usage.reasoning_tokens` 实测一两百到上千。

顺带修掉一处白等：面板拿到编排结果后**又跑了一次完整聚合搜索**来回填卡片
（原来按 `args.keyword` 重搜，跨 28 源 4–25 秒）。现在直接用 `calls[].data`
——那本来就是模型用它的关键词搜到的那批。

实机验证（MuMu / TV 0.9.40 形态，44 源）：
「我不是大师」**18s** 全流程（3 次模型往返 2.7/4.0/2.3s + 1 次搜索 + detail，卡片 6 张，只起 1 个搜索任务）；
「刚才后端报什么错了？」**5.5s**，模型自己选了 `meow_state → meow_logs` 并读出 7 条源侧 error；
「AI 搜索和搜索框有什么区别？」**5.0s**（此前必挂 8 秒）。

## 意图路由的三层分工（C2 的完整方案）

★ 这一节回答「AI 对话时是怎么分析该调哪个工具的」。

**和 ZCode 选技能是同一个机制：模型看描述选。** 区别只是我们的"技能"就是 11 个 `meow_*` 工具。

| 层 | 负责 | 在哪 | 依据 |
|---|---|---|---|
| **① 工具描述** | 模型决定调哪个工具（**主路径**） | `orchestrate.ts` 的 `TOOLS[].desc` | 每段 desc 写清「什么时候用」**和「什么时候不要用」** |
| **② 规则分类器** | 只做零成本的确定项 | `intent.ts` 的 `classifyIntent()` | 「播放X第一集」有明确结构；「就播它」是纯应答 |
| **③ 代码兜底** | 拦住误判的后果 | `tools.ts` 的 `meowSearch` | `keyword` 无实义时直接拒绝，不让它返回无关片 |

**每次请求都带全部 11 个工具的完整描述**：`orchestrate()` → `chatWithTools()` →
`toolSchemas()`（每次新建）→ `body.tools = [...]` + `tool_choice: 'auto'`。

实测 desc 长度：`meow_search` **200 字**（最长，因为它要写清禁止场景），
`meow_state` 33 字（最短）。`meow_search` 的关键段落：

```
仅在用户这句话里出现了新的片名时使用。
以下情况不要调用：用户说「那就放它吧/就这个/好/行」这类应答词
（应直接用上一轮的 site+vod_id 调 meow_play）；用户说「还有别的吗/换个源」
（用上一轮结果，不要重搜）；用户描述的是类型而非片名。
keyword 只能填片名本身，绝不能把整句话或应答词填进去。
```

**分类器只在高置信度时生效**（16 个用例实测）：

```
播放庆余年第二季第一集  → play | 庆余年第二季 #1
庆余年有第二季吗      → search | 庆余年
庆余年好看吗         → search | 庆余年
那就放它吧 (有上文)    → confirm        ← 直接播，零模型调用
那就放它吧 (无上文)    → chat           ← 指向不明，交模型
为什么播不了         → diagnose
这部没弹幕           → danmaku
还有别的吗 (有上文)    → followup       ← 用上一轮结果，不重搜
找个下饭的喜剧        → chat           ← 泛化需求，交模型追问
```

**为什么不全部交给正则**（走过的弯路）：把语义硬编码成正则，是在替模型做它擅长的事。
弱模型确实会犯错，但解法是**把描述写准 + 加代码兜底**，不是把判断权收回到正则。
正则只该处理"百分之百确定"的结构（动词+集数、纯应答词）。

## 零、为什么不是"AI 点界面"

这个想法方向对（AI 操作应用），但当前 18 个 `pc_*` 工具**全是 UI 原语**，用它做产品功能有三个硬伤：

| 问题 | 实测依据 | 后果 |
|---|---|---|
| **慢** | `pc_dom` 单次几十毫秒；一次"帮我找部片"要 5–10 轮 DOM 往返 + 2–3 次推理 | 十几秒，用户早自己点了 |
| **脆** | DOM 结构一变就点错；`pc_wait` 超时只能重试 | 静默点错比报错更难查 |
| **用户看得见** | 屏幕上的按钮自己动，没有 loading 态 | 像 bug，不像功能 |

**所以真正该做的是"语义工具"**：一次调用完成一件事，AI 不需要理解 DOM。

★ `pc_eval` 已经能执行任意 JS，**所以不需要任何新机制**——只是把高频意图固化成工具。
底层全是包装现有 REST，**零新业务逻辑**。

## 一、语义工具清单

分类标准：**价值 = 调用频次 × 单次节省的往返数**。

> **落点在前端**（`src/ai/tools.ts` 存实现，`src/ai/orchestrate.ts` 的 `TOOLS` 表存给模型的 schema）。
> 应用内 AI 直接调用；外部 AI 客户端（ZCode 这类）需要 MCP 协议时，由客户端的壳
> 把这些定义翻译成 `tools/list` 暴露出去。
> **后端不参与工具层。**
>
> ★ **同步的三份清单**：`tools.ts` 的 `TOOL_DEFS`、`orchestrate.ts` 的 `TOOLS`、
> `bridge.ts` 的 `TOOL_IMPL`。实测漏过 3 个导致模型看不见，现由两个测试
> （`工具清单完整性`、`外部 MCP 工具桥`）逐名断言，漏一个就红。
>
> ★ **外部 MCP 已复用其中 10 个工具**（v0.9.22，§1.8；`meow_cache_start` 为写操作不暴露）。PC 的 `pc_*`（18 个）与
> TV 的 `tv_*`（13 个）仍保留，两条路并存。

### 1.1 必用（缺了 AI 无法有效工作）

| 工具 | 包装的现成端点 | 为什么必用 |
|---|---|---|
| **`meow_state`** | `/api/health` + `/api/sites` + `/api/health/state` + `/api/logs?limit=200`（**只取概况**） | **AI 的"眼睛"**。任何操作前先建立上下文：版本、站点数、哪些源降级、日志各级条数与模块名。**日志正文不在这里**——只给 `logCounts` / `logTags`，具体内容让模型自己调 `meow_logs` |
| **`meow_diagnose`** | `__playerDebug` + `__meowDiag` + `/api/logs` + 当前路由 | **核心价值**。一次把"为什么播不了"的因果链拼出来（详见第二章） |
| **`meow_search`** | `POST /api/search` | 最常用入口。返回结构化 `{影片, 来源[{site, vod_id}]}`，而不是让 AI 从 DOM 读卡片 |

### 1.2 常用（覆盖 80% 日常操作）

| 工具 | 包装 | 说明 |
|---|---|---|
| **`meow_logs`** | `GET /api/logs?limit=2000`，筛选在**前端**做 | 查后端日志。用户问"刚才报什么错/为什么失败"，或诊断证据不够时用它。**看多少条、什么级别、哪个模块、多长时间窗全由模型决定**（见下方说明） |
| **`meow_play`** | `/api/{site}/detail` → `/api/{site}/play` → 跳播放页 | 一次完成"选集 + 选线路 + 播放"。**内部必须带失败换线**（§1.6） |
| **`meow_sources`** | `/api/sites` + `/api/health/state` | 源健康清单（可用 / 自动降级 / 手动停用 + 最近错误） |
| **`meow_cache`** | `/api/cache/grouped` + `/api/cache` | 查缓存：已缓存哪几部、各下到第几集、占多少空间、有无在下载 |
| **`meow_cache_start`** | `/api/{site}/detail` → 逐集 `/api/play` 解析直链 | 缓存一部片。**只解析、不下载**——见下方说明 |

**`meow_logs` 为什么把筛选交给模型**（2026-11-02 加）：

原来看日志只有 `meow_state` 里的"最后 20 条"，而实测运行中的缓冲区里
那 20 条**全是** `GET /api/...` 请求噪音、warn/error 零条 —— AI 拿到的
"最近日志"信息量为零，真出事时那条 error 早被挤出窗口。

但也不能反过来硬编码"warn 以上取 50 条"：正常时全是 info req，真出事时
warn/error 才有信息，**两种状态的正确采样完全不同**，写死哪一条都是猜。
所以把判断交给模型：先不带条件取 50 条看 level 分布，再决定收窄
（"刚才报什么错" → `minLevel:'warn', minutes:5`；"后端是不是卡了" →
`tag:'req', limit:100`）。`meow_state` 的 `logTags` 就是这个参数的候选清单。

三端各自有一份注册表（`orchestrate.ts` 应用内编排、`bridge.ts` 外部 MCP、
PC `mcp.rs` / TV `DebugServer.java`），**漏一处该端就看不见这个工具**，
所以 `ai-logs-tool.test.ts` 逐个断言。

**`meow_cache_start` 为什么只到"提议"为止**（2026-10-30 加）：

下载是写操作，要花流量和磁盘，按 §4.9 纪律二不能由模型自主决定。
所以这个工具只做**无副作用**的那一半——把每集的可下载 m3u8 直链解析出来，
返回一份 `CachePlan`（多少集、哪些直链、海报、剧名），交给界面弹确认卡；
用户点「开始下载」才真正入队（`AiPanel` 的 `confirmCache`）。

解析放在确认**之前**，是为了让确认框能显示"共 12 集"这种可判断的信息；
放后面会让用户面对一个"点了确认却卡十几秒"的按钮（整季 24 集要逐集打 `/api/play`）。

`meow_cache` 读的是 `/api/cache/grouped`（一剧一条）而不是平铺 list：
用户问"我缓存了什么"要的是「我不是大师 3 集」，平铺 list 会给 24 行"我不是大师 1/2/3…"，
AI 复述出来全是噪音。

> **工具数与拆分**：`meow_cache_start` 单独一个工具，没有并进 `meow_cache` 的
> `action` 参数。理由是 description 是模型唯一能看到的信息——
> "查缓存"和"缓存这部片"是两种完全不同的意图，塞进同一个 description 会让
> 模型在该查的时候去下、该下的时候只查。

### 1.3 提升体验（有增益，非必需）

| 工具 | 包装 | 增益 |
|---|---|---|
| **`meow_library`** | `/api/library` | 片库浏览。TV 上读 U 盘时这是唯一入口 |
| **`meow_danmaku`** | `/api/proxy/danmaku/search` | 弹幕源诊断（"这部为什么没弹幕"） |
| **`meow_live`** | `/api/live` + `/api/live/playlist` | 直播频道与坏台情况 |

### 1.4 明确不该做成工具

| 端点 | 原因 |
|---|---|
| `/api/proxy/stream` | 媒体流，AI 不该碰（会把几百 MB 灌进上下文） |
| `/api/config/import` | 破坏性操作 |
| `POST /api/policy` | 能改坏缓存目录等关键配置 |
| `/api/transcode` | 长任务（分钟级），AI 等不起 |

**规模建议：11 个**（3 必用 + 5 常用 + 3 体验）。再多会稀释选择——
模型在 20 个相近工具里挑，准确率明显下降。两次破例：
`meow_cache_start` 有明确且高频的触发词（"帮我缓存/下载下来"）且 description
与 `meow_cache` 完全互斥；`meow_logs` 是**补 `meow_state` 的信息缺口**——
原来那条"最近日志"是假的（见 §1.2），而把采样规则写死等于替模型做判断。
两者都不与既有工具争抢选择。

### 1.5 schema 直接引用契约，不另写一份

工具能不能被调对，全看 schema。**不要为工具另写一套参数说明**——
入参出参引 docs/26 的契约，工具层只做"最少必要参数"的收敛：

| 工具 | 必填入参 | 其余由前端 api 层补默认值 |
|---|---|---|
| `meow_state` | 无 | — |
| `meow_logs` | 无 | `minLevel` 默认 info、`limit` 默认 50（上限 500）。**筛选条件全由模型给**，工具层不做采样决策 |
| `meow_diagnose` | 无 | `scope` 默认 `play` |
| `meow_search` | `keyword` | `limit` 默认 5 |
| `meow_play` | `site` + `vod_id` | `episode` 默认「续播点 → 第 1 集」；`line` 默认自动选 |
| `meow_sources` | 无 | `onlyProblem` 默认 `true` |
| `meow_cache` | `action` | `site`/`vod_id`/`episodes` 按 action 需要 |
| `meow_library` | 无 | `path` 默认根目录 |
| `meow_danmaku` | `title` | `episode` 默认当前集 |
| `meow_live` | 无 | `group` 默认全部 |

★ **参数越少越好**：模型填 5 个参数的错误率明显高于填 2 个。能用默认值就别暴露。

### 1.6 请求形态：站点分派只能用 POST

★ **`/api/{site}/{action}` 的全部动作必须用 POST**。

分派层是 `read(ex.getRequestBody())` 后直接 `call(site, action, body)`，
**完全不看 query**。写成 `?ids=xxx` 会拿到空 body。

这个 bug 特别阴，因为它**不报错**：

```
GET  /api/AppGet/detail?ids=17688  → 200  {list:[{vod_name:null, vod_play_url:""}]}
POST /api/AppGet/detail  {id:17688} → 200  {list:[{vod_name:"庆余年 第一季", vod_play_url:"...6871字节"}]}
```

于是 `meow_play` 走到 `parseLines('')` 得 0 条线路，报"该片没有播放源"；
模型换线路重试全部同样失败——而**手动点播放（走 POST）完全正常**，
从界面上看就是"AI 坏了但应用没坏"。

★ 显式路由（`/api/health`、`/api/live`、`/api/proxy/danmaku/search`）是 GET + query，
不受影响。只有走站点分派的那几个要用 POST。判断方法：路径形如 `/api/{site}/{action}`。

### 1.7 `meow_play` 的换线算法

它是 11 个工具里唯一"必须一次做对"的——失败会直接暴露给用户。

```
候选线路 = detail 返回的线路表
排序：源健康 OK 优先 → 历史失败次数少的优先 → 原顺序
对每条线路：
  play(flag, id)
  parse === 1 → 先 POST /api/parse
  url 不是 http，或以 .jpg/.png 结尾 → 判坏（占位图），跳过
  起播看门狗 20s（只看 readyState，durationchange 不算）
  失败 → 记该线路失败（带影片信息）→ 下一条
最多试 3 条；3 条全坏 → 返回 {ok:false, cause, 失败原因列表}
```

三条硬约束：

- **最多 3 条**：★ 这是**新约束**，现状是无限换（`nextLineCandidate` 会一直试到没有候选）。
  工具层必须自己加封顶，否则 AI 一次调用可能试十几条线路、耗时几分钟
- **失败记录必须带影片**：现状是全局 key `meow.play.failedLines`
  （`PlayView.vue:493`，只存线路名字符串，只在错误页「重试」时清空）——
  看完 A 片再换 B 片，A 片坏掉的线路名还在，B 片会被无理由跳过
- **没有可用 url 时绝不假装成功**——宁可返回失败，让 UI 显示真实错误

**注意 `meow_play` 与现有播放页的职责边界**：换线逻辑现在**已经在播放页里**
（`PlayView.vue:340-380`，三条失败路径——`parse` 无解析器、`!play.url`、`catch`——
各自都做了 `addFailedLine` + `nextLineCandidate` 自动换线）。
工具层不要重写一套，应该**抽成共享函数**供两边调用，否则同一套规则会有两个版本。

## 二、诊断：规则先行，LLM 可选

### 2.1 两段式

★ **不能让 LLM 做诊断，只能让它做补充解释。** 这是整个方案最重要的决定。

```
用户点悬浮按钮「诊断」/ AI 调 meow_diagnose
   ↓
第一段：确定性归因（无 LLM，< 100ms）
   采集：__playerDebug + __meowDiag + /api/logs + 当前路由
   规则库匹配 → 结构化结论 {cause_code, confidence, evidence[], suggestion}
   ↓
第二段（可选）：LLM 解释 / 追问
   结构化结论 + 脱敏后的证据 → 人话 / 回答追问
```

**四条理由**：

1. **延迟**：规则 100ms vs LLM 1–3 秒。用户已经等了 20 秒起播超时，不能再叠 3 秒
2. **可靠性**：LLM 判错会导致"该换线的没换"；规则判错最多文案不准
3. **成本**：规则部分零成本
4. **可审计**：`cause_code` 是枚举，能统计"哪种失败最多"

### 2.2 LLM 到底加什么价值

★ **这一节是为了防止"为了智能而智能"。**

规则层已经自带中文文案（§2.6 的 `suggestion.text`），所以 LLM **不是翻译器**。
它只在三件事上有增量：

1. **多因并存时判断主因**——规则只能平铺列出（"403 且缓冲为空且弹幕 0 条"），
   人要知道"哪个才是根因"
2. **长尾**——规则不命中的未知错误串、协议异常、多个源同时坏
3. **追问**——"换个源会丢进度吗""为什么昨天还好"

**如果这三条都不需要，就只做规则层，把 LLM 整段砍掉——收益损失不大。**
文档保留 LLM 章节是为了这三条，不是因为"要有 AI"。

### 2.3 规则库（判据按 hls.js 事件写，不按 `video.error.code`）

★ **先说清为什么不能照直觉写**：`video.error.code` 只有 4 个枚举，
「占位图」和「编码不支持」都会落到 `MEDIA_ERR_SRC_NOT_SUPPORTED(4)`，**DOM 层面区分不开**。
真正可用的判据是 hls.js 的 `data.details` + `data.response.code`
（`VideoPlayer.vue:932-935` 已经在取这两个值）。

这些 cause_code 全部来自本项目的实际排障记录：

| cause_code | 判据（hls.js `details` / `response.code`，或对应数据源） | 建议动作 |
|---|---|---|
| `SOURCE_PLACEHOLDER` | `manifestParsingError` 且 `response.code` 为 200（源把 HTML / 图片当清单返回） | 换线路 |
| `SOURCE_403_REFERER` | `manifestLoadError` / `fragLoadError` 且 `response.code` ∈ {401, 403} | **自动**补 Referer 重试（`api/index.ts:482` 已把 header 透传给代理）；仍失败则换线路 |
| `HLS_RELATIVE_404` | `fragLoadError` 且 `response.code` 为 404，且 `data.frag.url` 与清单同主机（说明后端没改写成功） | **应用缺陷**，报给我们 |
| `CODEC_UNSUPPORTED` | `bufferAddCodecError` / `bufferAppendError`，或无 hls 网络错误但 `video.error.code === 4` | 转码或换源 |
| `NETWORK_TIMEOUT` | `manifestLoadTimeOut` / `fragLoadTimeOut`，或 20s 起播看门狗到期而 `readyState < 3` | 换线路 |
| `SOURCE_EMPTY_LIST` | `search` / `detail` 返回空 list（后端健康度已把它计为失败，见 `recordHealth`） | 源失效，换源 |
| `DANMAKU_ONLY` | `readyState >= 3` 但 `/api/proxy/danmaku` 返回 0 条 | 弹幕问题，不影响观看 |
| `CORS_BLOCKED` | 后端日志 `tag=cors` 出现 `blocked origin`（`ApiServer.java:429`） | 后端 CORS 配置 |
| `WEBVIEW_TOO_OLD` | 样式探针：`getComputedStyle(el).display` 为空（TV 壳 `MainActivity` 已有探针） | 设备内核过旧，见 docs/36 的排障章节 |
| `PARSE_REQUIRED` | `play.parse === 1` 且未调 `/api/parse`，或 play 的 url 不是 http 开头 | 前端漏调解析 |

**优先级**：`blocking`（播不了）> `degraded`（能播但体验差）。
一次命中多条时全部列出，主因判断按 §2.2 交给 LLM 或规则内的固定优先级表。

### 2.4 数据来源与缺口

★ 原有版本写的是"数据已就绪，无需新增采集"——**这句不准确**。实测有**四处**断点：

| 数据 | 位置 | 缺口 |
|---|---|---|
| 播放器状态 | `__playerDebug`（`VideoPlayer.vue:723` 的 `collectDebug()`） | 够用 |
| hls.js 错误 | `__playerDebug.lastError`（`:769`，内容形如 `fragLoadError (403)`） | ★ **致命错误不回写**：`:934` 只在 `!data.fatal` 时写，而致命错误才是要解释的那个 |
| 前端请求 | `__meowDiag.net`（`diagnostics.ts`） | ★ `MAX_NET = 100`（`:32`），hls.js 的分片 XHR 会把播放前的关键请求冲掉 |
| 后端请求 / 错误 | `GET /api/logs` | ★ 只记 `method + path`（`ApiServer.java:631`），**无状态码、无 query**；且分片会冲缓冲（见下） |
| TV 原生播放态 | 无 | ★ 需要新增桥方法（`NativePlayerActivity` 已知成功/失败，但不回传） |

**第 4 条是个独立的现存 bug**：`LogRoutes.isNoisyPath`（`LogRoutes.java:34-43`）里的过滤前缀是
`/proxy`（`:42`），而实际路径是 `/api/proxy/stream`——`"/api/proxy/stream".startsWith("/proxy")`
为 false，**分片请求根本没被过滤**。播一集几百个分片就能填满 2000 条缓冲，
日志面板在播放时不可用。

结论：把「分片 403 / 404」当判据的规则，今天**没有任何一处能稳定取到证据**。
必须先做 §2.5。

### 2.5 前置修复（四条，都小，但必须做）

| # | 改哪 | 改什么 | 为什么 |
|---|---|---|---|
| **1** | `VideoPlayer.vue:934` | 把 `lastHlsError` 的写入挪到 `if (!data.fatal)` 之外 | 致命错误现在不回写，而那正是要解释的失败 |
| **2** | `LogRoutes.java:42` | 补 `path.startsWith("/api/proxy/")` | 前缀匹配不到分片路径，缓冲会被冲干净 |
| **3** | `handleStream` 失败分支 | 分片 / 清单请求失败时记一条 `warn("stream", status + scrub(url))` | 现在只记 SSRF 拦截（`ApiServer.java:5028`），403/404 一条不记 |
| **4** | `diagnostics.ts:32` | 分片 XHR 不进 `net`（或另开一个只记失败的数组） | `MAX_NET=100` 会被分片冲掉 |

**诊断证据缓冲的设计要点**：诊断用的和面向人看的日志**过滤规则天然冲突**
（前者要静音成功、只留失败；后者要覆盖全量但排除高频路径），
所以不要共用同一个判断函数。1、2 是一行改动；3、4 各约 10 行。

### 2.6 输出契约

```json
{
  "ok": true,
  "cause": {
    "code": "SOURCE_PLACEHOLDER",
    "confidence": "high",
    "severity": "blocking"
  },
  "evidence": [
    {"kind": "hls", "detail": "manifestParsingError, HTTP 200, URL <源m3u8>"},
    {"kind": "player", "detail": "readyState=0, currentTime=0, 20s 未起播"},
    {"kind": "backend", "detail": "[proxy] blocked redirect ..."}
  ],
  "suggestion": {
    "action": "switch_line",
    "text": "这个源把视频换成了占位图（非应用缺陷），建议换线路",
    "options": ["线路2", "线路3"]
  },
  "explanation": "（可选，LLM 生成的 1–3 句人话；未配置 LLM 时为 null）"
}
```

★ `explanation` 为 `null` 时前端**只显示 `suggestion.text`，UI 不做任何区分**——
用户不该看到"你没配模型所以只有半套功能"。

**枚举取值（只有这几档，不要自由发挥）**：

| 字段 | 取值 | 含义 |
|---|---|---|
| `confidence` | `high` / `medium` / `low` | 判据是否唯一命中。多个规则同时命中时降一档 |
| `severity` | `blocking` / `degraded` / `info` | `blocking` = 完全播不了；`degraded` = 能播但有问题；`info` = 只是提示 |
| `evidence[].kind` | `hls` / `player` / `network` / `backend` / `style` | 证据来自哪一层 |
| `suggestion.action` | 见 §2.8 | 必须能被前端执行 |

**没有命中任何规则时**：返回 `{ok: true, cause: null, evidence: [...], suggestion: {action: "none", text: "未发现已知故障特征"}}`。
**不要编一个 `UNKNOWN` cause**——`cause: null` 让上层能区分"没诊断出问题"和"诊断出未知问题"，
前者是好事（视频本来能播），后者才需要上报。

**`ok: false`** 只用于诊断本身失败（比如 `__playerDebug` 不存在、读日志超时），
此时 `cause` 也是 `null`，但 `error` 字段给出原因。

### 2.7 诊断结论要贴在现有错误页上，不是只放 FAB 里

★ 这里有个容易做错的判断：**播放失败时用户看的是错误页，不是 FAB**。
如果诊断结论只在悬浮面板里，用户得先意识到"要点那个按钮"才看得到。

现有错误页已经有四个按钮（`PlayView.vue:1147-1185`）：

| 现有按钮 | 显示条件 |
|---|---|
| 用原生播放器打开 | TV 且 `canUseNative` |
| 换个线路 | `lines.length > 1` |
| 重试 | 总是 |
| 返回 | 总是 |

**正确做法**：把 `suggestion.text` 作为一行说明插到错误文案下面，位置在现有提示
（`isFetchError` / `allLinesFailed` 那两段 `p.text-xs`）之前；`suggestion.action`
对应的高亮按钮放到按钮组最前面。

这样用户不需要学习任何新交互——失败时该看的结论就在原来的位置。
悬浮按钮的定位见 §三。

### 2.8 `suggestion.action` 必须能被执行

只给文案等于"AI 说了一句"；要闭环就得把 action 定成枚举，并映射到前端已有函数：

| action | 前端执行 | 要用户确认 |
|---|---|---|
| `switch_line` | 调换线路逻辑，进下一条候选 | 否 |
| `switch_source` | 用同片名换一个 site 重新 search → play | 否 |
| `retry` | 重放当前地址 | 否 |
| `refresh_danmaku` | 重新拉弹幕 | 否 |
| `open_logs` | 跳 `#/logs` | 否 |
| `transcode` | `POST /api/transcode`（分钟级任务） | **是** |
| `disable_source` | `POST /api/health/degrade` | **是** |
| `none` | 只展示结论 | — |

★ 未知 action 一律降级成 `none`（只展示），**不要猜**。

## 三、对话入口：悬浮按钮

★ 先明确一件事：**诊断的主入口是错误页（§2.7），不是这个按钮。**
这个按钮解决的是"没有现成错误页，但用户有话想问"——例如"为什么这么卡"
"弹幕怎么没了""这片有第二季吗"。两者的数据源是同一个 `diagnose()`。

### 3.1 形态

一个悬浮按钮（FAB），**不新开页签、不打断当前页面**。

| 项 | 决定 | 理由 |
|---|---|---|
| 位置 | `fixed bottom-6 right-6` | 拇指可达 |
| 尺寸 | 56px（TV 72px） | 触控目标下限 44px；TV 是 10-foot UI |
| 收起态 | 圆形按钮 + 图标，无文字 | 不占版面 |
| 展开态 | 半屏面板：宽 ≤ 420px、高 ≤ 容器 70% | 保留页面上下文可见 |
| **播放页** | **隐藏 FAB**（`Ctrl+K` 仍可用） | 播放页已有错误页集成（§2.7）+ 四块浮层（选集/线路/弹幕/更多）在抢位；再放一个按钮只会互相遮挡。播放中用户要看的是控件 |
| **z-index** | **`z-[60]`** | ★ 必须高于顶栏 `z-30`（`AppHeader.vue:86`）和播放器底栏 `z-30`、面板 `z-40`（`VideoPlayer.vue:2812/3376`），低于居中弹窗 `z-[120]`（`CenterDialog.vue:53`）和伪全屏 `z-[100]` |
| **伪全屏时** | FAB 一并隐藏 | 直播页也有伪全屏（`LiveView.vue:556`，`z-50`，低于 FAB 的 `z-[60]`），不藏就会被 FAB 压在上面 |
| 遮罩 | 无全屏遮罩 | 点面板外区域才收起，播放不暂停 |

**层级顺序（实测自现有代码）**：

```
背景 z-0 → 内容 z-10 → 顶栏 z-30 → 播放器底栏 z-30 / 面板 z-40
  → AI FAB z-[60] → 伪全屏 z-[100] → 居中弹窗 z-[120]
```

★ 不要给 FAB 用 `z-50`：Tailwind 的 `z-50` 和 `z-[100]` 之间只差一层，
但现有代码里 `z-40` 的面板是播放器的"更多/选集/线路"，FAB 盖住它们会挡住主操作。

### 3.2 一次完整交互

```
点 FAB → 面板展开
输入"播放庆余年第一集" → 回车
  ├─ 面板显示进度："正在搜索 28 个源…"
  ├─ 命中唯一：结果卡片（片名 / 源 / 集数 / 「▶ 播放」）
  ├─ 命中多部：列 3 个候选，各带一个「▶ 播放」
  └─ 命中 0：直接说没搜到，不猜
点「▶ 播放」→ 跳播放页 → 起播 → 进全屏
```

**面板里要显示工具调用过程**（一行折叠文案即可，如"已查 3 个源，正在取播放地址…"）。
理由：搜索跨 28 个源可能要几秒，没有进度就是"点了没反应"。

### 3.3 桌面端要有键盘入口

Web/PC 用户手在键盘上时，鼠标点 FAB 是多余的。快捷键走现有播放器同一套约定：

- **`Ctrl/Cmd + K`** 打开输入焦点（`Ctrl+K` 是通用搜索约定）
- **`Esc`** 关闭面板
- 播放页的快捷键处理里，判定修饰键已存在（`VideoPlayer.vue:1996` 的 `if (e.ctrlKey || e.metaKey || e.altKey) return`），
  所以 `Ctrl+K` 不会与播放器现有的 `f` / `d` / `Esc` 冲突

★ 不要用单键（如 `a`）：播放器已有 `f`/`d`/`Esc`（`VideoPlayer.vue:2051-2061`），
再占一个字母迟早冲突，而且用户不知道。

TV 不绑快捷键——遥控器的按键全被 `tv-nav.js` 接管了。

### 3.4 语音输入：用系统能力，不自己接麦克风

★ **我们不做语音识别**。理由：TV/手机的系统输入法本身带语音键，
那是系统级能力，识别质量远好于我们自建；自建要 `RECORD_AUDIO` 权限 +
一个 ASR 服务 + 一份费用，收益为负。

实测：`AndroidManifest.xml` 只有 `INTERNET` 一个权限，前端也
`grep -rn 'SpeechRecognition|getUserMedia'` 零命中——**现状是干净的，别破坏它**。

所以"一句话播放"里的"一句话"，是**用户对着输入法说**，输入法转成文字后
前端拿到的就是普通字符串。我们要做的只有：输入框接收任意文本、支持粘贴、支持长文本（≤100 字截断）。

★ 后端 `ApiServer.java:421` 的 CORS 白名单决定了 `getUserMedia` 类能力在不同来源下
行为不一，自己接语音会引入一堆 origin 相关问题——又一个不做它的理由。

### 3.5 结果卡片要"可执行"，不是"可阅读"

AI 返回的每一行必须是能点的一个动作，而不是一段描述。三种卡片：

| 卡片 | 内容 | 点击 |
|---|---|---|
| **影片卡** | 海报 + 片名 + 年份 + 命中的源数量 | 展开来源列表 |
| **来源行** | `源名 · 集数 · 健康状态` | 「▶ 播放」 |
| **动作卡** | `建议：换个源 / 换条线路 / 重试` | 直接执行（写操作仍要确认） |

★ 片名、源名这些**来自第三方站点的字符串必须当纯文本渲染**，
禁止 `v-html`。实测前端目前零处 `v-html`，保持这个状态；
送进模型时也要包在明确的分隔里（如 `<<片名>>`），避免提示词注入。

### 3.6 为什么"播放"必须留一次点击

两个平台限制都绕不过去：

1. **全屏**：`requestFullscreen()`（`VideoPlayer.vue:1561`）要求**用户激活**，
   Chrome 的窗口约 5 秒。从回车到播出来要过 search → detail → play 三次网络往返，很容易超时
2. **自动播放**：浏览器要用户手势才允许出声

所以 UI 上必须留这一次点击。它同时解决两个问题，**而且让"AI 猜错了"的补救成本降到零**——
看到片名不对，不点就是了。

兜底已经存在：容器全屏被拒时会自动降级成**伪全屏**（`enterPseudoFs`，`:1523`，
纯 CSS 撑满视口，不需要用户手势），弹幕层和控制栏都保留，只是不隐藏浏览器地址栏。

| 端 | 真全屏 | 自动出声 | 结论 |
|---|---|---|---|
| **TV** | 不需要——`NativePlayerActivity` 本身是全屏 Activity | ExoPlayer 无策略限制 | 全自动 |
| **PC** | WebView2 通常允许，仍受激活窗口限制 | 一般允许 | 大概率自动 |
| **手机浏览器** | 大概率落伪全屏 | ★ 必须有手势 | 必须点一次 |

**可选的真全屏优化**：用户回车后立刻跳播放页 + 立刻请求全屏（还在激活窗口内），
页面里再异步搜索取地址。代价是播放页要多一个"自然语言入口"形态，
收益只在 PC 上（手机上无论如何都要点）。**不建议一期做。**

### 3.7 TV 上的形态差异（只有焦点，没有功能分叉）

**TV 上也放输入框。** TV 的输入法是系统能力——多数盒子/投影仪的遥控器带语音键，
输入法内部就把语音转成文字，**这部分完全不需要我们做**。

实测依据：现有搜索页的输入框（`SearchView.vue:170`）在 TV 上已经用软键盘工作，
manifest 也配了 `windowSoftInputMode="adjustResize|stateAlwaysHidden"`
（`AndroidManifest.xml:22`），说明这条路早就打通了。

TV 只需额外处理三件事：

- FAB 要能被方向键导航（`tabindex` + 焦点环，现有 `tv-nav.js` 已处理方向键）
- 面板内的按钮和输入框要能被方向键遍历，焦点环必须可见
- 输入框显式请求焦点时才弹键盘——`stateAlwaysHidden` 是为了首页不自动弹，
  对话框里的输入框需要主动 `focus()`

★ **不要为 TV 单独做一套"只能看结论"的降级形态**。那会让同一份前端出现两条分叉路径，
以后每次改面板都要改两处。TV 与 Web/PC 唯一的差异是**焦点可见性和触控目标尺寸**。

## 四、模型与编排

### 4.1 落点：客户端，不在后端

AI 是**客户端能力**：用户在哪台设备上说话，模型调用和编排就在哪台设备上发生。
后端保持"哑"的 REST 服务，**不知道 AI 存在**。

四条理由：

1. **三端跑的是同一份前端**——PC 的 `tauri.conf.json:10` 是 `frontendDist: "../../web/dist"`，
   TV 的 `MainActivity.java:302` 直接 `loadUrl(后端首页)`。AI 写一次，Web / PC / TV 全有
2. **纯本地场景也要能用**——用户只挂个 U 盘片库、没有后端部署时，AI 不该失效
3. **key 是用户配置，不是服务配置**——放后端等于"每个用户必须自建后端才能用 AI"
4. **证据在客户端**——`__playerDebug` / `__meowDiag` 都在页面里，
   规则和编排挨着数据放，省一次往返，也不怕后端版本落后

```
前端 src/ai/
├── tools.ts        11 个语义工具（包装现有 src/api/ 函数）
├── loop.ts         编排循环：prompt → tool_calls → 执行 → 再调模型
├── rules.ts        诊断规则库（读 __playerDebug / __meowDiag / /api/logs）
├── evidence.ts     只记失败的证据缓冲（§2.5 第 4 条）
├── prompt.ts       系统提示词常量（§4.8）
└── settings        模型配置，存客户端 prefs（与 meow.api 同层）
```

**原来设想的 `llm-helper` 插件取消**——没有后端插件这回事了。

★ 全部 lazy import：`import('./ai/panel')` 在用户第一次打开面板时才加载（§6.1）。

### 4.2 出站怎么发：壳代理，不是浏览器直连

★ **浏览器 `fetch` 直连模型 API 会被 CORS 挡住**。OpenAI / DeepSeek 这类厂商
不返回 CORS 头（是它们的策略，不是浏览器限制），所以不能假设前端能直连。

| 环境 | 出站路径 | 成本 |
|---|---|---|
| **PC** | 新增一个 Tauri command，Rust 侧已有手写 HTTP 能力（`mcp.rs:1174`） | ~30 行 |
| **TV** | 新增一个 `TvBridge` 方法，OkHttp 已在依赖里（`build.gradle:118`） | ~30 行 |
| **纯 Web（无壳）** | 见下三选一 | — |

纯 Web 只有浏览器，三条路：

1. **后端可选转发** `/api/llm/relay`，`policy.json` 里 `llmRelay.enabled` **默认 false**，
   只转发不存 key、不参与编排。它是兼容层，不是 AI 主体
2. **本地 Ollama**：`OLLAMA_ORIGINS` 可放行跨域，等于零成本离线
3. 不提供

走壳代理的主要好处是**绕开 CORS**，以及**不走浏览器的 fetch 栈**（少一层被页面 hook 拦截的面）。

★ 但不要说"key 不进浏览器存储"——**prefs 本身就是 localStorage**（`prefs.ts:156` 的 `meow.prefs`），
WebDAV 密码也同样存在那里（`prefs.ts:402` 的 `meow.webdav`）。
所以 LLM key 与现有凭据是**同一安全水位**，不是新增风险，也没变好。
真要加固应该整体迁移（比如 PC 用 Tauri store、TV 用 SharedPreferences），
不要只给 LLM key 单独上一套——那会让人误以为其他凭据是安全的。

### 4.3 配置存客户端 prefs

与 `meow.api` 同层，不进后端 `policy.json`。

★ **`Prefs` 是平铺结构**（`prefs.ts:13` 的 `interface Prefs`），不要嵌套成 `llm: {...}`：

```jsonc
// meow.prefs（localStorage）里的新增字段
{
  "llmEnabled": false,
  "llmBaseUrl": "https://api.deepseek.com/v1",
  "llmApiKey": "",
  "llmModel": "deepseek-chat",
  "llmTimeoutMs": 8000,
  "llmMaxTokens": 300
}
```

三条实现要点：

1. 字段同时加进 `interface Prefs` 和 `DEFAULTS`，否则类型检查过不了、旧用户读出 `undefined`
2. **迁移/判断必须读 `raw` 不能读合并后的 `out`**——合并过 DEFAULTS 之后
   `out.llmEnabled` 恒为 `false`，`if (out.x === undefined)` 这种判断会变成死代码（踩过）
3. `llmApiKey` 与 WebDAV 密码同为明文，见 §4.2 的安全水位说明

在 TV 上填这些不是问题：`PushServer.java` 已经实现「手机扫码填配置推给电视」，
填 key 和填后端地址走同一条路；TV 的输入法也能用语音输入代打。

**配置入口放哪**：设置页的 `ai` 分区「AI」（2026-10-30 起为独立一级分区）
（`SettingsView.vue:1683` 的 `NAV_ITEMS`）。三端都显示，不做端过滤——
TV 也需要在这里填 key。

**未配置时悬浮按钮仍然可用**：面板首屏显示「模型未配置 · 点此设置」，
但**诊断结论照常输出**（规则层不依赖 LLM）。不要做成"没配 key 就禁用按钮"。

### 4.4 多提供商：支持，但用 OpenAI 兼容协议统一

**关键事实**：几乎所有主流厂商都提供 OpenAI 兼容端点，包括本地 Ollama。

| 提供商 | baseUrl | 兼容性 |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | 原生 |
| DeepSeek | `https://api.deepseek.com/v1` | ✅ 兼容 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | ✅ 兼容 |
| 月之暗面 | `https://api.moonshot.cn/v1` | ✅ 兼容 |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | ✅ 兼容 |
| **Ollama（本地）** | `http://127.0.0.1:11434/v1` | ✅ 兼容 |
| Anthropic | — | ❌ 协议不同 |

**建议：只实现 OpenAI 兼容协议一种**，`baseUrl` + `model` 由用户自填。理由：

- 一套代码覆盖 90% 场景（**含本地 Ollama，等于可以零成本离线用**）
- 用户想换模型只改一个字符串，不用等我们适配
- Anthropic 走兼容网关（one-api / LiteLLM）即可

**二期可选**：加 `provider: "anthropic"` 分支，内部转 `messages` 格式，约 40 行。

### 4.5 模型选择要"可自填"不是"可下拉"

★ 不要做固定下拉列表。模型迭代太快，写死的列表半年后全是过时的。
正确做法：**预设常用值 + 允许任意输入**（`<datalist>` 或"自定义"选项）。

### 4.6 编排循环的五条硬约束

| 约束 | 值 | 为什么 |
|---|---|---|
| 最大轮数 | **8** | 防死循环。正常一次任务 2–4 轮 |
| 单轮超时 | 8s | 模型 + 工具合计 |
| 总超时 | 30s | 超过就给当前最好结论，不再尝试 |
| 历史保留 | 最近 4 轮 | 控制上下文增长 |
| 同工具同参数连续 2 次 | 判定死循环，立即终止 | 模型常见退化行为 |

★ **工具结果必须摘要化再喂给模型**，这是最容易写崩的地方：

| 工具 | 喂给模型的内容 |
|---|---|
| `meow_search` | 前 5 部 × 每部前 3 个源（名称 / site / vod_id） |
| `meow_play` | `{ok, url 是否 http, format, qualities 数量, 失败原因}`——**不回完整地址** |
| `meow_state` | 版本 + 站点计数 + 降级源名单（最多 10 个） |
| `meow_sources` | 只回有问题的源 |
| 任意工具结果 | 超过 2KB 截断，并附「（已截断）」 |

理由：跨 28 个源的原始搜索结果有几十 KB，直接塞进上下文既费钱又会让模型抓不住重点。

### 4.7 失败模式清单

| 失败 | 行为 |
|---|---|
| 模型返回不存在的工具名 | 忽略该调用，回一条"没有这个工具，可用：…"，最多重试 1 次 |
| 参数类型 / 必填缺失 | 回 schema 校验错误让它重试 1 次，再错放弃 |
| **幻觉片名**（search 返回 0） | 直接说"没搜到 xxx"，**绝不猜别的片** |
| 死循环（同工具同参 2 次） | 终止，给出已有结论 |
| 上下文超限 | 丢最早对话轮，保留系统提示 + 最近 2 轮 |
| 401 / 403 | 提示"密钥无效"，**不重试** |
| 429 / 超时 | 静默降级到规则结论（红线 2） |
| 工具自身失败（后端 500） | 把错误摘要给模型，允许它换源重试一次 |

### 4.8 系统提示词要自带 domain

模型不认识我们的术语，不问就会乱猜。系统提示必须包含**五块**：

1. **人设**：猫窝的看片助理，说人话、有判断、承认不知道（见 §4.9.1）
2. **这是什么应用**：自建影视聚合客户端，内容来自"源"（第三方站点解析）
3. **术语表**：源 / 线路（同一部片在不同源的多个播放地址）/ jar 站 / drpy 站 /
   ext / parse / 弹幕源——每个一句
4. **可用工具清单** + 什么时候该调哪个（含"绝对不要搜索"的反向约束）
5. **明确禁止**：不编造片名；不说"已帮你切换"（除非工具返回成功）；不输出完整 URL

输出要求写死：短句、先结论后动作、不超过 3 句。

提示词放前端常量（`src/ai/prompt.ts`），不跟用户消息混在一起。
加了人设与缓存用法两段后约 2200 字符（≈880 token），
`tests/ai-orchestrate.test.ts` 卡了这个上限，防止顺手再加长文。

### 4.9 四条实现纪律

| 纪律 | 具体 | 为什么 |
|---|---|---|
| **状态只信工具返回** | UI 上的任何变化（换了线路、开始下载）必须由工具执行结果驱动，**不能由模型文字驱动** | 模型会说"已帮你切换"，而它只是说了一句 |
| **写操作要人确认** | `meow_cache_start` 只解析不下载（结果交 UI 弹确认卡）、`transcode`、`disable_source` 一律不进编排 | 会消耗带宽/磁盘或影响其他片，不能让模型自主决定 |
| **无后端要快速降级** | 启动先 `meow_state`；失败则工具集收敛成"只读本地片库"，并在面板上说明 | 纯本地用户不该看到一串 500 错误 |
| **成本要可见** | 设置页显示本次会话累计 token / 调用次数；一次诊断解释约 800 in + 150 out，一次搜索对话约 3–5k in | 用户自己付费，有权知道花在哪 |

★ 第三条与 §八 的"AI 只读"不冲突：**读操作自由，写操作一律确认**。
这是两条不同的线，别混成一个布尔。

### 4.9.1 `[已实现]` 人设（2026-10-30）

原来只有"规则 + 禁止 + 输出"，模型是个无性格的诊断器：不认自己是猫窝的一部分，
也不会把"你想看这部"接成"要不要我帮你缓存下来"。

人设块（`prompt.ts` 的 `PERSONA`）给的是**身份与边界**，不是让模型演角色——
演过头会让回答变长、跑题，反而降低工具准确率。三条自我限制都是踩过的坑：

| 限制 | 理由 |
|---|---|
| 不报名字时不强行自我介绍 | 每次开头"我是猫窝助理"会挤掉结论句 |
| 不卖萌、不用表情、不自称"喵" | 一旦开始"喵～"，后续工具结果也会被包成可爱腔，用户报障时读到会以为没在认真处理 |
| 只承诺做得到的事 | 写影评、查上映/评分/演员不在客户端能力内，硬答就是编造 |

"能做/做不到"是显式列出来的，因为用户最常问的恰恰是后者（评分、上映日期）——
直接说查不到，比"建议你去豆瓣看看"好（用户来这里就是想少开一个 App）。

诊断提示词（`DIAG_SYSTEM_PROMPT`）**只借语气，不加长**：它只需 1–3 句。
`llm.ts` 里还有一份独立的 `SYSTEM_PROMPT`，三处说法必须一致，改一处要同步三处。

### 4.9.2 `★ 单一开关`：设置页的「启用」就是唯一权威（2026-10-30）

**踩过**（用户反馈"已经启用了，怎么还有开关控制"）：系统里有两个开关——

| 开关 | 存哪 | 作用 |
|---|---|---|
| 设置页「AI 启用」 | 前端 localStorage `llmEnabled` | 之前**只**管前端要不要走 AI 这条路 |
| `policy.json` 的 `llmRelay.enabled` | 后端 | Web/TV 调模型**必须**经 `/api/llm/relay`，这里默认 `false` |

于是用户打开开关、填好 Key、点测试，仍然收到"后端没开模型中转"，
而界面上**没有任何地方能改那个 policy**。

现在前端这个开关是唯一权威：一变就自动把后端 `llmRelay.enabled` 同步成同值
（`SettingsView.vue` 的 `syncRelaySwitch`）。policy 字段保留（自建实例仍可在
配置文件里强制关闭），但用户不需要知道它存在。同步失败不报错——
PC 走壳、根本用不到 relay。

> **这条的通用教训**：一个用户可见的开关背后如果有第二个开关，
> 用户永远只会找到第一个。要么合并，要么把第二个暴露出来。


### 4.10 答案要流式输出

非流式时，用户回车后要等模型把整段话生成完（1–3 秒）才有任何反馈，
中间面板是空的。**必须有流式**：SSE 或分块读取，边生成边显示。

三条约束：

- **工具调用轮次不流式**——那一轮本来就没内容，显示"正在思考…"即可
- **最终回答那轮流式**——首字延迟目标 < 800ms
- **壳代理必须支持流式**：Tauri command 与 TvBridge 方法都不能等整包返回。
  OkHttp 用 `ResponseBody.source()` 逐块读；Rust 侧用 `mpsc` 把 chunk 回推给前端
  （Tauri 的 `emit` 事件机制）

★ 现有代码里 `grep -rn 'text/event-stream|EventSource|ReadableStream'` 三处皆零命中，
说明这是**全新能力**，不是复用。估工时已算进 §七 步骤 5（该步已从 0.5 天调成 1 天）。

若不实现流式，退而求其次：显示"生成中…"骨架 + 首字延迟 3 秒。
但用户会觉得卡。

### 4.11 本地缓存：同样的诊断不要重复问模型

同一个 `cause_code` + 同样的证据特征，解释文案是一样的。缓存能省一半调用：

- key = `cause_code` + `evidence` 的摘要（不含 URL）
- 值 = `explanation` 文本，有效期 7 天
- 存 localStorage，上限 50 条（LRU）
- **不带片名、不带 URL**，所以缓存本身不含隐私

★ 只缓存 `explanation`，不缓存对话——对话有上下文，缓存了会答非所问。

## 五、三道安全与降级红线

| 红线 | 具体要求 | 为什么 |
|---|---|---|
| **1. 默认关闭** | `llmEnabled: false`，没配就不调 | 不打扰不用的用户，也不产生意外费用 |
| **2. 失败静默降级** | LLM 超时 / 401 / 限流 → 直接返回第一段规则结论 | ★ **绝不阻塞诊断** |
| **3. 出口脱敏** | 发给 LLM 的证据先在客户端替换掉自己知道的敏感值 | ★ **最危险也最易漏** |

脱敏要做两层：客户端发请求前替换自己 prefs 里的密码（能精确知道原文，替换最彻底）；
后端日志那一侧已经由 `LogBuffer.scrub()` 把 `url=/token=/password=/pwd=` 打码成 `***`。

★ 还有一层常被忽略的隐私：**片名和源站 URL 本身也是隐私**
（能看出用户在看什么）。建议默认只发 `cause_code` + 结构化证据摘要，
不发完整 URL；提供「只发本地规则结论、不发证据」的开关。

## 六、三端差异

三端跑同一份前端，所以 AI 逻辑只有一份；差异全在**出站通道**、**诊断数据**和**输入方式**。

★ 错误页集成（§2.7）和悬浮按钮（§三）在三端是**同一份代码**，不需要端过滤。
下表只列真正需要分叉的部分。

| 端 | 诊断数据 | 模型出站 | 输入方式 |
|---|---|---|---|
| **Web（手机/桌面浏览器）** | `__playerDebug` + `__meowDiag` + `/api/logs` | 无壳时需后端 relay 或本地 Ollama | 输入框 + 系统输入法；桌面端 `Ctrl+K` |
| **PC** | 同上 + CDP（可选，额外取证） | Tauri command 直发 HTTPS | 同上 |
| **TV** | 同上；★ 播放态要额外从 `NativePlayerActivity` 读（需新桥方法） | `TvBridge` 方法直发 HTTPS | 输入框 + 系统输入法（含语音转文字）；仅焦点环与触控目标尺寸有别 |

★ TV 的 `DebugServer` 绑 `0.0.0.0` 带 token，那是给**外部 AI 客户端**用的通道，
与应用内 AI 无关。应用内 AI 不需要它，也不需要打开那个开关。

★ TV 的内核是 Chrome 66，`fetch` 可用，但要确认 `AbortController` 行为；
前端 AI 模块不要用可选链以外的 ES2020+ 语法（构建目标已是 es2017，
但手写字符串模板时容易漏）。

### 6.1 体积预算（实测基线）

当前主包 `index-*.js` **158KB（gzip 58KB）**，`hls-*.js` **580KB**（lazy chunk，已分离）。

AI 模块的增量估算：

| 模块 | 估算 | 说明 |
|---|---|---|
| `tools.ts` + `rules.ts` + `prompt.ts` | ~15KB | 纯逻辑，无依赖 |
| `loop.ts` | ~8KB | fetch + 状态机 |
| 面板 UI（一个 .vue） | ~10KB | 复用现有组件 |
| **合计** | **~33KB（gzip ~11KB）** | 相对 58KB 主包约 +19% |

**结论：可接受，但必须满足两条**：

1. **AI 模块要 lazy import**——不在首屏 chunk 里。用户不开 AI 就不下载
2. **不引第三方 SDK**——OpenAI 兼容协议就是 HTTP POST + JSON，手写 100 行足够；
   引 `openai` npm 包会增加 200KB+ 且带 Node 依赖

★ TV APK 现在 7MB 级别，+33KB 无感；但 TV 的启动时间对包体敏感，
lazy 那条对它比 PC/Web 更重要。

## 八、明确不做的（避免走弯路）

| 想法 | 为什么不做 |
|---|---|
| AI 找片 / 自然语言搜索（"找个下饭的喜剧"） | 源是**关键词搜索**不是语义检索。LLM 只能把它翻成关键词，源站要精确片名，翻了也搜不到 |
| AI 推荐 / 猜你喜欢 | 没有行为数据（只有观看历史），冷启动无解 |
| AI 生成弹幕 / 评论 | 污染弹幕生态，无用户价值 |
| AI 总结剧情 | 片源是盗链，无字幕轨可读；`subs` 字段覆盖率极低 |
| 内嵌本地大模型 | 投影仪 4GB 内存、OECT `-Xmx512m`，跑不动。但**本地 Ollama 走 HTTP 可行**（§4.4） |
| 让 AI 直接改配置 / 删缓存 | 破坏性，出问题难回溯。AI 只读 + 建议，**写操作一律等用户点确认**（§4.9） |
| 为"看起来智能"而调模型 | 见 §2.2：规则已经能说人话，LLM 只在三件事上有增量 |

## 十、验收标准

每一步做完怎么验，写死在这里，避免"改完了但不知道算不算完成"。

| 步骤 | 验收方式 | 通过判据 |
|---|---|---|
| **0 前置修复** | 播一集，然后 `GET /api/logs?limit=50` | 返回里**没有** `GET /api/proxy/stream`；故意播一个坏源，日志里有一条带状态码的 `stream` 失败 |

| **2 错误页集成** | ★ 播放失败时**不点任何按钮**，直接看错误页 | 结论已显示在错误文案下方，建议动作按钮在按钮组首位 |
| **2 错误页集成** | 现有四个按钮（原生播放器/换线路/重试/返回）各点一次 | 行为与改动前**完全一致**，没有任何回归 |
| **3 悬浮按钮** | 首页、片库页、设置页各点一次 | 1 次点击出中文结论 + 建议动作；无 LLM 也完整可读 |
| **3 悬浮按钮** | ★ 播放页 | FAB **不显示**（错误页已覆盖诊断）；但 `Ctrl+K` 仍能打开面板 |
| **3 悬浮按钮** | 非播放页三处 + 播放页各看一次 | 不遮挡顶栏、卡片和弹幕面板；TV 上方向键能导航到并展开 |

| **6 编排循环** | 故意说一个不存在的片名 | 明确回"没搜到"，**不幻觉、不猜别的片** |
| **6 编排循环** | 人为让模型返回不存在的工具名 | 一次重试后放弃并给出已有结论，不死循环 |
| **6 编排循环** | ★ 说"帮我切换到线路2" | 模型若只回文字说"已切换"而没调工具，UI **必须不变**（§4.9 纪律 1） |
| **7 relay（可选）** | 关闭时 / 打开时各测一次 | 关闭时行为与之前完全一致 |
| **8 打磨（可选）** | 同一坏源连续诊断两次 | 第二次**不发模型请求**（命中解释缓存），文案一致 |
| **8 打磨（可选）** | 桌面端按 `Ctrl+K` | 面板打开且输入框获焦；`Esc` 关闭；播放器 `f`/`d` 不冲突 |
| **体积** | `pnpm build` 后看主 chunk | AI 模块**不在首屏 chunk**；主包 gzip 增量 ≤ 15KB |
