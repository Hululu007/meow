## 二、根因：拿"编码名"一刀切，跳过了设备能力

当前逻辑问的是 **"这是什么编码"**（10-bit → 转码），
正确逻辑应该问 **"这台设备能不能解这个文件"**。

- H.264 Hi10P：WebView 和多数电视硬解都只吃 8-bit → 转码是对的；
- HEVC Main10 / AV1 10-bit：电视原生播放器通常能解，且是 4K HDR 的标准形态
  → 一律转码等于把能原画看的片砍成 1080p 8-bit，用户看到的就是"降画质"。

代码注释写的是「10-bit **H.264**（Hi10P）是共同盲区」，但结论被错误泛化到了所有
10-bit。这就是本次要修的核心。

## 三、目标链路：能力优先，逐级降级

```
直连(direct) → 原生播放(native) → 转封装/视频copy(remux)
    → 硬件转码 1080p + tonemap(transcode-hw)
    → 软件转码(transcode-sw) → 明确失败(fail)
```

**原则：每一级只在上一级"真的做不到"时才走。** 不是按端名（TV/PC/手机）猜，
而是按实测能力决定。

### 3.1 三类能力分开算

| 能力 | 来源 | 用途 |
|---|---|---|
| WebView 能解什么 | `MediaSource.isTypeSupported()` 按 container/codec/profile/位深实测 | 决定能不能直连 |
| 原生播放器能解什么 | TV 桥新增 `nativeCaps()`：`MediaCodecList` 查 HEVC Main10 / AC3 / DTS / 4K / HDR | 决定能不能原生原画 |
| 转码能做什么 | 后端 `/api/transcode?action=caps`：hw/sw、最大输出、tonemap 是否可用 | 决定转码档位 |

### 3.2 路由纯函数（单一判定入口）

现有 `resolvePlaybackRoute()` 已经是纯函数 + 17 个用例门禁，这是好底子，
**在它上面扩展，不要另起炉灶**：

```ts
type Mode = 'direct' | 'native' | 'remux' | 'transcode-hw' | 'transcode-sw' | 'fail'

function decide(probe, caps): Mode {
  if (caps.web.canDirect(probe)) return 'direct'       // 全可解：行为完全不变
  if (caps.native?.supports(probe)) return 'native'    // 电视硬解，原画
  if (caps.remux(probe)) return 'remux'                // H.264 8bit ≤1080：视频 copy
  if (caps.transcode.hw) return 'transcode-hw'         // 1080p + tonemap
  return caps.transcode.sw ? 'transcode-sw' : 'fail'
}
```

`highBit` 从顶层判断里**删掉**，下沉成 `canDirect()`/`supports()`/`remux()` 内部条件：

- H.264 Hi10P → 三关都不过 → 转码；
- HEVC Main10 → TV 原生过 → `native`；PC/Web 不过 → 转码（此时必须带 tonemap）；
- H.264 8-bit 1080p + AC3 → Web 音频不过、原生过 → `native`；无原生 → `remux`（视频零损失）。

### 3.3 probe 补字段（后端 `probeMedia()`）

现有六个字段不够判断 HDR，补：

- `bitDepth`（8/10/12）
- `colorTransfer`（`smpte2084` / `arib-std-b67` 判 HDR）
- `channels`（5.1/7.1）
- `container`（mkv/mp4/ts）

探测失败时返回 `{ok:false}` 的语义**保持不变**，前端降级为直连 + 运行时检测，
行为与旧版一致（这是最重要的一条不回归保证）。

## 四、设备矩阵（"兼顾不同设备最高需求"的具体含义）

| 片源 | TV（原生支持） | PC / Web | 手机 |
|---|---|---|---|
| 1080p H.264 8-bit + AAC | 直连 | 直连 | 直连 |
| 1080p H.264 8-bit + AC3 | 原生（原画） | remux：视频 copy + AAC | 同 PC |
| 4K HEVC Main10 HDR + AC3 | **原生 4K HDR** | 转码 1080p + HDR→SDR | 按 MSE 能力，不行再转码 |
| H.264 Hi10P | 转码 1080p | 转码 1080p | 转码 1080p |
| 4K H.264 8-bit | 原生 4K | 转码 1080p | 视能力 |

不是让所有设备都看 1080p，而是**每台设备拿它能解的最高画质**。

## 五、不回归门禁（改之前先认这几条）

1. **直连条件不变**：`decide()` 第一顺位仍是现有 `direct` 判断，支持的文件行为一字不动。
2. **probe 缺失走旧逻辑**：`{ok:false}` → 直连 + 运行时兜底，绝不主动转码。
3. **原生失败才降级**：原生播放器报错 → `native-failed` → 转码；转码失败才错误页，不循环。
4. **网络错误不转码**：保留 `shouldTranscode(kind)` 只认 `media/src/fake`，不加新类型。
5. **矩阵门禁**：`playback-route.test.ts` 拆成「H.264 Hi10P」和「HEVC Main10」两组，
   至少补 6 个用例（TV 有原生 / TV 无能力 / PC / 无转码 / probe 半残 / 8-bit 不误判）。
6. **开关可回滚**：`routingV2` 默认只对 TV 片库开，VOD / PC 保持旧逻辑；出问题一个开关关掉。
7. **不碰并发与看门狗**：`stopOtherJobs` / `hw_busy` 排队 / 空闲 120s 看门狗 / token 续播
   这一轮全部不动——它们刚实测通过，改了就是自己制造回归。

## 六、明确不要做的事（避免额外问题）

| 不要做 | 原因 |
|---|---|
| 不要改 4K→1080p 的帽子 | RK3566 硬编 0.28x，是硬件约束，不是策略 |
| 不要做 4K 软转 / 4K 硬编 | `slow_4k` 拦截保留，起这种任务只会烧 CPU、写满磁盘 |
| 不要给所有 10-bit 做 tonemap | 只对 HDR（PQ/HLG）做；SDR 10-bit 做 tonemap 会偏色 |
| 不要一上来改 hw 管线 | 先实测 `h264_rkmpp` 能否吃 `hwdownload` 后的 CPU 帧；不行就让 HDR 单独退回 `libx264`，别动整条硬编链 |
| 不要重做错误类型过滤 | #2 已修，`shouldTranscode()` 现成 |
| 不要自动切原生处理所有错误 | 1.2.21 踩过"任何抖动都整页跳到原生 Activity"的坑；只对探测确认的编码不支持做原生优先 |
| 不要把 `silentAction` 记忆当隐式规则 | 点过一次不能永久生效，必须有出口（见 P2） |

## 七、转码质量（只有必须转码时才做）

- HDR→SDR：只对 `colorTransfer=smpte2084/arib-std-b67` 启用 tonemap，
  输出显式 `-color_primaries bt709 -color_trc bt709 -colorspace bt709`。
- 码率：硬编 `5M → 8M`（局域网）/ 外网仍 5M；软编 `crf 23 → 20`，先在 OECT 量吞吐。
- 硬编 HDR 管线候选：`scale_rkrga` 降 1080p → `hwdownload` → `zscale/tonemap` →
  `h264_rkmpp`；若 `-22`，HDR 源退回 libx264 1080p，非 HDR 仍走原硬编。

## 八、落地顺序与验收

**P0（1.2.22 发布前必做，只动选路，风险最小）**

1. `playRoute.ts` 的 `highBit` 只对 h264 成立；片库预检与第三道拦截同步改。
2. 测试拆两组，补 HEVC Main10 用例；不碰转码器参数。
3. `routingV2` 开关默认只开 TV 片库。

**P1（单独开关、单独验收）**

4. probe 补位深/色彩/声道，转码加 HDR→SDR + 8M。
5. 先在 `.20` 实测 tonemap 吞吐（首片 ≤30s）与 `h264_rkmpp` 兼容性。

**P2**

6. 原生能力上报 `nativeCaps()`、播放页「原画 / 转码中 1080p」标识、
   `silentAction` 设置出口（每次询问 / 原生 / 转码）。

**验收清单（逐条给证据）**

- [ ] 同一部 4K HDR HEVC 片库片：TV 走原生，**不转码**，色彩正常
- [ ] 同一部片在 PC：转码 1080p，`ffprobe` 显示 `color_transfer=bt709`，不发灰
- [ ] H.264 Hi10P 仍转码（不被"HEVC 优先"带偏）
- [ ] 1080p H.264/AAC 仍直连（不回归）
- [ ] 网络抖动（断网 3 秒恢复）不触发转码
- [ ] 非 HDR 源耗时与现状持平（tonemap 链不生效）
- [ ] OECT 转码首片 ≤30s、持续 ≥1.2x 实时（给实测数字）
- [ ] `silentAction` 可从设置改回「每次询问」
