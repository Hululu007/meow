# 全 JVM 加载器验证 · Java 21 定案（2026-11-24，`feat/fongmi-loaders`）

> 前置：[全JVM加载器验证-2026-11-24.md](./全JVM加载器验证-2026-11-24.md)（Java 9 兼容性结论）
> 本轮目标：**放弃 Java 9 兼容，按 Java 21 处理**，验证 GraalJS/GraalPy 能否承载我们全部源，并给出融入方案。

## 一、GraalVM 是谁开源的（核实）

| 项 | 值 |
|---|---|
| 项目 | [oracle/graal](https://github.com/oracle/graal)（GraalVM） |
| 组件 | GraalJS（JS）、GraalPy（Python）、Truffle 框架、polyglot API |
| 许可 | **GraalVM Community Edition = GPL-2.0 with Classpath Exception**；SDK / Truffle / TRegex = **UPL**（Universal Permissive License）；GraalJS Maven 工件 = UPL 1.0 |
| Maven | `org.graalvm.js:js`、`org.graalvm.python:python` / `python-community`、`org.graalvm.polyglot:polyglot` |

许可对商用友好（Classpath Exception / UPL），不构成使用障碍（风险标注，不否决）。

## 二、Java 版本定案

| 目标 | 选择 |

## 三、GraalJS 实测（Java 21 上也验证）

用 `graal21-libs`（GraalJS 21.3.0，major=52，Java 8+ 通吃）在 Java 8 已跑通 jumi.js 真实搜索

若用新版 GraalJS（25.x）需 Java 21，本目标下可选，但 21.3.0 已够用。

**结论：JS 源全 JVM 化 = 可行（已实测真实数据）。**

## 四、GraalPy 实测（Java 21，本轮核心）

### 4.1 环境搭建（可复现）

```bash
# 1) Java 21（解压到 tmp，未改系统）
curl -sL "https://api.adoptium.net/v3/binary/latest/21/ga/windows/x64/jdk/hotspot/normal/eclipse" -o jdk21.zip
unzip -q jdk21.zip   # jdk-21.0.13.1+2

# 2) 依赖（polyglot 24.1.0 + python-language/resources + truffle 全套）
mvn -gs settings-central.xml -s settings-central.xml -f pypom.xml \
    dependency:copy-dependencies -DoutputDirectory=py-libs

# 3) 纯 Python 包（requests/urllib3/certifi/charset_normalizer/idna/bs4/soupsieve）
#    从本机 CPython site-packages 拷进 GraalPy 的 python-home/Lib/site-packages
```

### 4.2 三个关键坑（实测踩过，写进方案）

1. **`ModuleNotFoundError: requests`**：GraalPy 只解压 python-home，不含三方包。
   → 必须把纯 Python 包放进 `python-home/Lib/site-packages`，并在 Context 里
   `ctx.getBindings("python").putMember("_SP", sp)` + Python 侧 `sys.path.insert(0, _SP)`。
   （C 扩展包如 lxml 另需 GraalPy 版，纯 py 的 bs4 可直接用。）
2. **SSL 警告**：`urllib3 v2 only supports OpenSSL 1.1.1+` / `unable to enumerate Windows certificate store`
   → 是警告不是错误，网络实际通（HTTP 200 已验证）。
3. **冷启动 ~9s**：首次构建 python-home 缓存；后续 Context 复用会快。

### 4.3 真实源测试结果（Java 21 + GraalPy 24.1.0）

| 源 | 关键词 | 结果 |
|---|---|---|
| **hsck** | 国产 | **RESULT n=40，FIRST 約19小嫩妹…** ✅ |
| missav | test | n=0（CPython 同期也是 0，站点失效，非引擎问题） |
| mw | TEST | n=0（CPython 同期也是 0，站点失效） |
| kpsp/mdtv | — | n=0（站点波动） |

同时验证：`requests.get()` 在 GraalPy 内 **HTTP 200**（网络栈可用）。

**结论：Python 源在 JVM（Java 21 + GraalPy）上可用——同样的脚本、同样的依赖、同样的结果；返回 0 的站与 CPython 一致，是站点问题。**

## 五、融入方案（Java 21 全 JVM）

### 5.1 架构

```
后端 JVM（Java 21）
  ├─ csp_/jar        → 现有 JarLoader（DexClassLoader）不动
  ├─ CMS(type=1)     → 现有 CmsSource 不动
  ├─ *.js            → 新增 GraalScriptSource：Graal Context("js")
  │                     注入 req/pdfh/print（照 drpy host.js 的全局实现）
  │                     兼容 var spider={__jsEvalReturn} 导出
  └─ *.py            → 新增 GraalPythonSource：Graal Context("python")
                        python-home 随镜像分发（内置纯 py 包）
                        base.spider 兼容层（补 getCache/fetch/host）
```

各端不再需要 node/py 外挂插件——**运行时就是后端 JVM 本身**。

### 5.2 依赖与打包

| 依赖 | 版本 | 说明 |
|---|---|---|
| Java | 21（Temurin） | 各端 JVM 统一升 21 |
| `org.graalvm.js:js` | 21.3.0 或 25.x | 21.3.0 兼容性最好；25.x 需 Java 21 |
| `org.graalvm.python:python-community` + `python-resources` | 24.1.0 | GraalPy 引擎 + python-home |
| `org.graalvm.polyglot:polyglot` | 24.1.0 | polyglot API |
| 纯 py 包 | 拷贝/graalpy-maven-plugin | requests/bs4/urllib3/certifi/idna/soupsieve |

镜像方案：python-home（含 site-packages）打进 apiserver 镜像 ~100MB；首次启动预热 Context。

### 5.3 改造清单（按优先级）

1. **后端加 Graal 依赖**（pom/manifest），新增两个 `ScriptSource` 分派：按 api 后缀走 js/py。
2. **JS 全局适配层**：把 drpy host.js 的 `req/pdfh/pdfa/pd/joinUrl/md5/base64` 实现翻成 Java host 对象绑定到 polyglot bindings；`print` → 日志。
3. **Python 兼容层**：`base.spider` 桩（补 getCache/fetch/host/getProxyUrl）+ python-home site-packages。
4. **Context 池化**：避免每个请求冷启动 9s——按站点 key 缓存 Context（Fongmi 也是按 spider 实例缓存 JS Context）。
5. **各端去掉 node/py 插件**：PC/TV/fpk 的 drpy 插件、NodeService、pyrt 都可下掉（前提：后端升 Java 21）。
6. **Fongmi/TVBox**：仍是外部消费者，继续吃 config+jar；Graal 是我们后端内部能力，不影响它们。

### 5.4 风险

- **启动内存**：GraalPy python-home + Context 常驻，单实例内存增加（估 200~400MB，需压测）。
- **C 扩展**：lxml/pycryptodome 等含 C 的包 GraalPy 支持有限（实测纯 py 包没问题；这批脚本的加密站可能要 GraalPy 专用版包）。
- **并发**：polyglot Context 非线程安全，需按站点池化 + 串行化调用（与 drpy worker 池同理）。
- **Java 21 升级面**：全端 JVM 从 17 → 21，涉及 PC 打包、Docker 镜像、TV 内嵌网关（Android JVM 是 ART，不适用——**TV 端网关跑的是 Java 字节码在 ART 上，GraalVM polyglot 需要真正的 JVM，TV 上要单独评估**）。

> ★ TV 特别说明：TV 的 ApiServer 是编译成 dex 跑在 ART 上，不是标准 JVM；GraalJS/GraalPy 的 Truffle 引擎需要 JVM 能力。**TV 端无法直接内嵌 Graal**（除非把整个引擎也 dex 化，未验证）。所以"各端去插件"对 PC/Docker 成立，TV 仍需 node/py 外挂或连远端 Java 21 后端。

## 六、结论

| 问题 | 答案 |
|---|---|
| GraalJS/GraalPy 谁开源 | Oracle GraalVM，CE = GPL-2.0+CPE / UPL |
| Java 21 上能跑我们全部源吗 | **JS ✅（真实数据）、Python ✅（hsck 40 条真实数据）** |
| 各端能去掉 node/py 插件吗 | **PC/Docker ✅**（后端 JVM 直接跑）；**TV ❌**（ART 非 JVM，需连远端或保留外挂） |
| 代价 | 后端升 Java 21 + 镜像 +~100MB python-home + Context 池化 |
