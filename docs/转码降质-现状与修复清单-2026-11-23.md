# 片库转码降质 · 现状与修复清单（2026-11-23）

> 交接文档：给单独处理「片库播放被转码 / 画质下降」这条线的会话。
> **所有结论按 `release-v1.2.21`（最新发布 tag，2026-11-20）核对**；
> 工作区 1.2.22 的未发布改动单独标注，不要拿来解释用户反馈。
>
> 相关 issue：<https://github.com/upchr/meow/issues/12>

---

## 一、结论摘要

1. 用户（飞牛 fpk 后端 + TV 客户端 + 本地片库）看到的"降画质"= **直连失败后被自动转码**，而转码参数在 1.2.21 就是 1080p 封顶 + 硬编 5 Mbps / 软编 CRF23 veryfast + **零 HDR→SDR 映射**。
2. 1.2.21 的转码触发**不过滤错误类型**：片库播放任何一次 `onPlayerError` 都会转码，包括网络抖动。
3. 4K 源被降到 1080p 是硬件约束（RK3566 编码器 1080p 级），**不是 bug**；HDR 不映射、码率过低才是。
4. 1.2.22（未发布）新增的 `highBit` 预判把**所有 10-bit（含 HEVC Main10）**判成"只能转码"，TV 上连原生播放都不试 —— **上线前必须改**，否则"4K HDR 一律转码"从偶发变必然。
5. `silentAction`（记住"转码/原生"选择）一旦点过就永久生效，设置页没有改回"每次询问"的入口。

## 三、1.2.21 的实际链路

### 3.1 直连判定（前端）

- `client/apps/web/src/views/PlayView.vue` 的 `cantPlayContainerDirectly()`：
  - Firefox → `false`（能解 mkv）
  - **Android（含 TV WebView）→ `false`** → MKV/HEVC **先直连**
  - 其余（桌面 Chromium / Safari）→ `true`，配合 `unsupportedContainer()` 按扩展名直接转码
- 结论：**TV 上不是"一律转码"**，是"先直连，失败才转"。

### 3.2 失败后转码（前端）

`onPlayerError()` 里：

```js
if (!transcodeTried && isLibraryPlay.value) {
  transcodeTried = true
  void tryLibraryTranscode(libraryLib.value, libraryFile.value)
  return
}
```

- 1.2.21 这里**没有 `shouldTranscode(kind)` 过滤**（该函数只作用于点播分支）。
- 后果：解码失败、音轨不支持、**网络抖动/超时**都会触发整集转码。
- 转码成功后在画面上飘 8 秒提示：`已转码播放（源文件未改动）` —— 用户"好像被转码了"的直接来源。

### 3.3 转码参数（后端）

`server/host/src/shared/core/Transcode.java` 的 `hlsCommand()`：

| 路径 | 参数 |
|---|---|
| 硬解硬编（检测到 `h264_rkmpp` 才走） | `-hwaccel rkmpp -hwaccel_output_format drm_prime`；4K → `scale_rkrga=w=1920:h=…:format=nv12`；`-c:v h264_rkmpp -rc_mode VBR -qp_init 23 -b:v <hwBitrate>` |
| 软编 | `-c:v libx264 -preset veryfast -crf 23`；`-vf scale='min(1920,iw)':-2` |
| 音频 | `copyAudio` 不成立时 `-c:a aac -b:a 192k -ac 2` |
| 色彩 | **没有任何 `tonemap` / `zscale` / `-color_primaries` / `-color_trc`** |

`hwBitrate()` 档位：输出高 `>900 → 5M`，`>600 → 3M`，其余 `2M`。

### 3.4 4K 的兜底

`slow4kHopeless()`：4K 且**没有硬编**且在 ARM 上 → 直接拒绝，错误码 `slow_4k`，文案提示"改用原生播放器"。这条**不会**静默降质。

### 3.5 1.2.21 的另一个已知缺陷（已由 1.2.22 修）

1.2.21 软编路径**没有 `-pix_fmt yuv420p`**：10-bit 源会让 libx264 输出 High10（`yuv420p10le`），浏览器仍解不了 → 表现为"转码了还是黑屏/失败"。1.2.22 已钉死 8-bit。

## 四、为什么画质明显下降（1.2.21 就存在）

| 维度 | 现状 | 后果 |
|---|---|---|
| 分辨率 | 4K → 1080p（硬编与软编都封顶 1920 宽） | RK3566 编码器只有 1080p 级，属平台约束 |
| 色彩 | **无 HDR→SDR 映射**，硬编还强制 `format=nv12`（8-bit） | BT.2020/PQ 数据进 8-bit SDR 管线：发灰、对比塌、灰阶断层 |
| 码率 | 硬编 1080p `5M`；软编 `crf 23 veryfast` | 片源常见 10–20 Mbps，5M 明显发软；veryfast 细节丢失 |

### 4.1 实机证据（2026-11-23，OECT `192.168.1.20`）

ffmpeg 版本 `8.1.1-mediasrv`，滤镜齐全：`zscale` / `tonemap` / `tonemapx` / `tonemap_opencl` / `tonemap_cuda`。

合成 10-bit BT.2020/PQ 片，分别跑「现状参数」与「加 tonemap 链」：

```
IN                   pix_fmt=yuv420p10le  space=bt2020nc  transfer=smpte2084  primaries=bt2020
OUT 现状(无 tonemap)  pix_fmt=yuv420p      space=bt2020nc  transfer=smpte2084  primaries=bt2020
OUT 加 tonemap 链     pix_fmt=yuv420p      space=bt709     transfer=bt709      primaries=bt709
```

现状 = **HDR 数据压成 8-bit 却仍贴 HDR 标签**：播放端按 HDR 显示就发暗 + 断层，按 SDR 解释就发灰。

复现命令（在 `.20` 上，用 `/tmp` 跑，别动服务）：

```bash
ffmpeg -hide_banner -loglevel error -y -f lavfi -i "testsrc2=s=320x180:r=24:d=2,format=yuv420p10le" \
  -c:v libx264 -pix_fmt yuv420p10le \
  -x264-params "colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc" h.mp4
ffprobe -v error -select_streams v:0 -show_entries stream=pix_fmt,color_primaries,color_transfer,color_space -of default=nw=1 h.mp4
ffmpeg -hide_banner -loglevel error -y -i h.mp4 -vf "scale=min(1920\,iw):-2" -pix_fmt yuv420p \
  -c:v libx264 -preset veryfast -crf 23 o_now.mp4
ffprobe -v error -select_streams v:0 -show_entries stream=pix_fmt,color_primaries,color_transfer,color_space -of default=nw=1 o_now.mp4
```

## 五、1.2.22（未发布）引入的新问题 · 上线前必须改

1. `client/apps/web/src/utils/playRoute.ts` 的 `resolvePlaybackRoute()`：

   ```ts
   if (highBit) return canTranscode ? 'transcode' : 'native-hint'
   ```

   - `highBit` 只看 `pixfmt`（`p0?(10|12|16)`），**不看视频编码**
   - 该分支排在 `hasNative` 之前 → HEVC Main10（4K HDR 的标准编码）也被判"只能转码"，TV 上拿不到 `native` / `native-hint`
   - 代码注释写的是「10-bit **H.264**（Hi10P）是共同盲区」，结论被错误泛化到了 HEVC

2. `PlayView.vue` 的 `known.probe` 分支：`if (highBit || (audioBad && remembered !== 'ask'))` → 直接 `onNoAudio()`，**连直连都不试**

3. `silentAction`：`useTranscodeFromHint()` 写入 `'transcode'` 后，入口判定 `remembered !== 'ask'` 会跳过直连；设置页只有 `nativeOnSilent` 开关，**没有改回 `ask` 的入口**

**如果不改就发 1.2.22**：所有 4K HDR（HEVC Main10）在 TV 上都会跳过直连与原生，直接转 1080p。

## 六、修复方案（建议顺序）

### P0-1 补充 HDR→SDR tonemap（1.2.21 已有问题）

软编路径插入：

```
zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=tonemap=hable:desat=0,zscale=t=bt709:m=bt709:r=tv,format=yuv420p
```

并显式：`-color_primaries bt709 -color_trc bt709 -colorspace bt709`。

- 只在源是 HDR（`transfer=smpte2084/arib-std-b67` 或 `primaries=bt2020`）时启用；SDR 源跳过，避免无谓开销
- **硬编路径的难点**：`-hwaccel_output_format drm_prime` + `scale_rkrga` 让帧留在显存，`zscale` 需要 CPU 帧。两条可选管线，需实测：
  1. `hwdownload,format=nv12,scale=1920:-2,<zscale tonemap 链>` → 再交给 `h264_rkmpp`（能保留硬编，但多一次下载/上传）
  2. 先 `scale_rkrga` 缩到 1080p，再 `hwdownload` 做 1080p tonemap（帧小，CPU 代价低）
- 备选滤镜：`tonemapx`（SIMD 优化版）可先做 A/B
- **性能红线**：OECT 上 4K HEVC Main10 → 1080p 首片现状 13.6s，加 tonemap 后不得超 30s

### P0-2 1.2.22 上线前：`highBit` 只对 h264 成立

```ts
const hi10p = highBit && video === 'h264'
if (hi10p) return canTranscode ? 'transcode' : 'native-hint'
```

- HEVC Main10 + TV 有原生桥 → `native`（ExoPlayer 硬解）
- HEVC Main10 + PC/网页 → 仍转码（它们确实解不了），但此时必须带 tonemap
- `PlayView.vue` 入口的 `highBit` 判断同步改，并带上 `vcodec`

### P1-1 提高 1080p 画质档

- 硬编：`5M → 8M`（VBR 可加 `-maxrate/-bufsize`）
- 软编：`crf 23 → 20`，`preset veryfast → faster`（先在 OECT 量吞吐）
- 先量后调：以"首片 ≤30s + 持续 ≥1.2x 实时"为约束（OECT 现状 1.28x）

### P1-2 转码提示写清降了什么

- 文案：`已转码 1080p（原片 4K HDR）`
- TV 壳给一个「用原生播放器看原画」按钮（`ErrorPage` 已有同类入口可复用）

### P1-3 错误→转码加类型过滤

1.2.21 的"任何错误都转码"应收敛：网络类先重试/换线路，只有解码/容器类才转码（1.2.22 的点播分支已有 `shouldTranscode(kind)`，片库分支照搬）。

### P2 设置页暴露 `silentAction`

三档：`每次询问 / 转码 / 原生`，默认 `ask`。

## 八、未决问题（交给下一轮先验证）

1. RK3566 上 `zscale` tonemap 4K 的实际吞吐（CPU 单线程），会不会把首片拖过 30s → 决定用 4K 还是先缩 1080p 再 tonemap
2. `h264_rkmpp` 能否吃 `hwdownload` 后的 CPU 帧（需实测 `-22` 风险）
3. TV WebView 对 4K HEVC 10-bit 直连的成功率（决定 1.2.22 里 HEVC 该走 `native` 还是 `direct`）
4. 用户实际片源编码（4K HDR 10-bit？1080p HEVC？音轨 AC3/DTS？）——没有设备现场，按上面通用结论覆盖
5. 硬编 `-b:v 8M` 在 RK3566 上的持续能力（会不会掉帧/发热降频）
