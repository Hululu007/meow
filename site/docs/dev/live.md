# 直播

直播的数据来自两处：源包的 `lives` 表和用户自己添加的 IPTV 地址。两者在后端聚合成一份频道列表，
前端再做**跨源合并**——同一个台出现在多个源里时合并成一条，线路放进池子。

## 一、两个来源

| 来源 | 从哪来 | 特点 |
|---|---|---|
| **站点直播表** | `config.json` 的 `lives` 字段 | 导入源包后自动出现；`type: 0` 是纯 m3u，`type: 3` 走 spider |
| **用户添加** | 直播页「添加源」填 m3u / txt 地址 | 存在前端本地，与站点配置互不影响 |

两者是**并列**的，不是覆盖关系。设置页的 `lives` 只影响站点那一半。

## 二、后端聚合：`/api/live`

```json
{
  "tried": 55,
  "failed": 12,
  "playlists": [{ "name": "示例源", "count": 42 }],
  "groups": [{ "name": "央视", "channels": [{ "name": "CCTV-1", "urls": ["..."] }] }]
}
```

| 字段 | 含义 |
|---|---|
| `tried` / `failed` | 尝试拉取的源数 / 失败数。**两者相等说明上游全挂，不是客户端问题** |
| `playlists` | 每个源拉到多少频道（用于判断哪个源失效） |
| `groups` | 合并后的分组与频道，`urls` 是该台的全部线路 |

聚合是**渐进式**的：不等所有源都返回，先到先出结果，慢源继续补。冷启动要等几个源，
不是一次请求就完整。

## 三、前端合并：`liveMerge.ts`

六个纯函数，可以单测：

| 函数 | 作用 |
|---|---|
| `normChannelName` | 归一化台名（去空格、全半角、常见后缀），用于判重 |
| `cleanChannelName` | 展示用的清洗（去掉 `[高清]`、`HD` 之类） |
| `zhGroupName` | 分组名中文化（`CCTV` → `央视`） |
| `mergeSources` | **核心**：把多个源的频道按归一化名合并成一条，线路汇总 |
| `sourceCountOf` | 这条频道有几个源提供 |
| `describeSources` | 生成「3 源」这种描述文本 |

### 去重的作用域：按分类，不跨分类

同一个台在「央视」和「4K 专区」各出现一次，**不会被合并**——因为分类不同的「CCTV-1」
对用户来说是两个可选项。全局去重会让频道数从几十缩到个位数。

### 归并后的线路池

一条频道下挂多个 URL，播放时按顺序试。**一条线路失败先把同台的其他线路试完，再换台**——
这两个动作在代码里是两个计数器（`lineTryCount` 与 `autoSkipCount`），不能合并。

## 四、坏台与坏线

```
播放失败
  ├─ 同台还有线路 → 换线路（lineTryCount++）
  └─ 线路试完     → 换下一个台（autoSkipCount++）
```

如果两个计数器合成一个，表现会是「一条死线导致整台被跳过」，用户看到的是「换台了但没播」。

## 五、缓存

- 前端把聚合结果缓存在本地，冷启动直接用缓存先出画面，后台再刷新
- 拉取 m3u 是主要耗时（公共源 6 s 量级），缓存把它挪出首屏
- 缓存过期后重新拉；用户手动「刷新」会强制拉

## 六、EPG

不做节目单。公共 EPG 源时效性太差，投入产出比低。

## 七、改这块之前

| 要改什么 | 先看 |
|---|---|
| 加一个直播源类型 | `/api/live` 的拉取分支 + `playlists` 计数 |
| 改去重规则 | `normChannelName` 有单测，改完跑 `pnpm test` |
| 改换台策略 | 两个计数器要分开，见上文 |
| 改缓存时长 | 前端缓存层 + 首屏策略 |
